# 0.2.0a1: core Telegram operations

Engineering alpha, prepared locally on 2026-10-20. Not published to PyPI, not a
production readiness declaration. The [0.1.0a2 report](0.1.0a2.md) records earlier
session/login repairs; this increment builds on those changes.

## Architecture and implementation

The client now exposes coherent peer, dialog, message, membership and media services,
rather than only identity/send/raw wrappers. Handwritten services issue actual
Telegram requests through the shared deadline/admission/error boundary. Algorithms
live in `peers.py`, `pagination.py`, `messages.py`, `dialogs.py` and `chats.py`;
Client is their public facade. No copied competitor implementation was added.

- User/chat/full-profile lookup, contacts and blocking/unblocking.
- Lazy dialogs with separate pins and date/ID/peer cursors; main/archive folders.
- Lazy newest-first history and search (optional sender), finite collection helpers,
  ordered message-ID retrieval with None for unavailable/other-chat messages.
- Literal-text sends/replies/edits, forwarding with secure random IDs, pin/unpin,
  read markers, and scoped deletion. Non-channel deletion preflights every ID before
  issuing any delete; channel deletion requires explicit revoke=True.
- Basic-group/channel member enumeration, user queries, explicit join/leave/invite.
- Bounded account-local peer cache, correct full/min access-hash handling, additive
  minimal session metadata, no fabricated hashes. Username bindings expire after
  60 monotonic seconds and are re-resolved after restart or explicit refresh.
- Command/media/chat-type filters, stable handler priorities, removal,
  StopPropagation and client-bound reply/edit/delete/download helpers. Dispatch starts
  after the client is ready; one sequential worker preserves documented ordering.
- Explicit streamed document/photo sends and confirmed server logout with local key,
  peer-cache and update-snapshot clearing. Logout is never implicit on disconnect.

MTProto authorization, encryption, connection recovery and update reconciliation still
use pinned **Telethon 1.45.0**. GramFlux is not yet a replacement independent protocol
engine. Raw result objects remain dependency types; use Client/event helpers for
GramFlux execution policy. Runtime dependency set is unchanged.

## Schema and compatibility

Official API snapshot retrieved 2026-10-20, page-advertised layer **225**;
SHA256 `13d9c9f4a4ecc7282725b5a558f719cea5af0c3bafcf62531cac3a18bfaca046`.
Independent output: **1573 constructors, 783 methods**, with all IDs and fields checked
against the retained official JSON; 46 explicit-ID protocol declarations parsed.
Runtime raw bindings come from Telethon layer **229**. Independent generated objects
remain offline-only and are rejected by Client.invoke. Neither count is live coverage.

Declared Python >=3.11; actually tested here: 3.11.17, 3.12.3, 3.13.16 and 3.14.8. CI targets 3.11–3.14,
but those jobs have not been observed running. Persistent storage requires POSIX
flock. No competitor-session or drop-in API compatibility. Session format remains
version 1 with optional peer metadata; older clients may discard that metadata.

## Performance and security

The measured 64-byte inputFile local microbenchmark remains slower in the independent
codec: encode median 10247 ns versus Telethon 3580 ns; decode 12790 ns versus 6921 ns.
See the raw versioned JSON for all rounds, Python/platform and traced allocations.
These are noisy local measurements of different validation policies, not network/file
throughput or proof of a regression. No performance superiority or optimization claim.

New protections include bounded minimal peer metadata, rejection of min access-hash
replacement, expiring username bindings, validated snapshot contents, scoped deletion
and explicit destructive channel semantics. Existing redacted errors/logging, secure
SQLite ownership/permissions and chunked transfer cleanup remain in place.

Keys and access hashes remain plaintext in protected session files. Updating/logout
cannot erase historic SQLite pages/backups or zero Python memory. Backend queues are
not globally bounded; update/callback delivery is not crash-transactional. No independent
cryptographic review or real-account fault-injection security audit was performed.

## Production blockers and next priorities

1. Run opt-in account/bot interoperability tests for login, SRP, reuse, history,
   members, messages, photos/documents and update reception; inject real disconnects,
   migrations and waits. Credentials must remain external and dedicated.
2. Make update queues and cursor persistence end-to-end bounded/crash-consistent;
   demonstrate gap/difference recovery and define callback acknowledgment semantics.
3. Audit encryption/session lifecycle and backend private hooks. Resolve the native
   schema/runtime layer split before claiming an independent MTProto implementation.
4. Implement tested cross-DC media authorization, CDN/reference refresh and resumable
   recovery before broad file-transfer promises.
5. Expand legitimate administration/media/bot operations with focused tests; profile
   realistic workloads and verify remaining Python/OS targets before production release.
