# 0.2.0a2: bounded uploads and streamed byte ranges

Local engineering alpha prepared 2026-10-20. Builds on the
[core operations increment](0.2.0a1.md). Artifacts have not been published remotely.

## Implemented behavior

- upload_file, send_document and send_photo accept part_size and concurrency.
  Default behavior remains 512-KiB parts and one outstanding part. Concurrency 1–16
  holds a bounded window of RPC tasks, using sequential source reads. Small-file MD5
  follows source order, independent of acknowledgment order. Progress is serialized
  and counts accepted bytes, which are not necessarily a contiguous resumable prefix.
- iter_download and iter_download_media yield bytes only when requested, without
  prefetch. Arbitrary offset/length edges are trimmed from aligned protocol requests.
  Downloads validate exact known lengths and respect Telegram's 1-MiB request windows.
- download_file/download_media support the same exact byte ranges; media also accepts
  caller-owned binary destination streams. Path targets contain only the selected
  bytes, are published atomically without overwrite, and return Path. Streams return
  None and remain open. This return annotation is broader than the previous media API.
- Cancellation/error joins outstanding upload parts. Repeated cancellation during
  source open, temporary-file allocation or disk writes cannot abandon a newly
  acquired handle or close it while a worker is still using it. A blocked OS/custom
  stream operation can still delay cancellation until it returns.
- Photo selection uses the largest supported size and skips empty progressive lists.
- New stream_hash.py example hashes a selected media range without writing it to disk.

Algorithms remain in files.py, with thin Client methods. No new runtime dependency,
compiled extension, proprietary cryptography, blanket retries or competitor source
was introduced. Runtime encryption/authorization/update recovery still use Telethon
1.45.0. The bounded upload window shares the ordinary client connection, not dedicated
media DC connections. See the [file guide](../guides/files.md) for precise contracts.

New tests cover out-of-order acknowledgments/checksums, bounded reads and active tasks,
large/small paths, flood failure without retries, task cleanup, partial/nonzero-position
stream reads, invalid/oversized data, lazy reads/early close, unaligned range edges,
1-MiB boundaries, property-tested byte equality, invalid 64-bit ranges, zero ranges,
progress, no-overwrite/temporary cleanup, CDN rejection and public client routing.
Thread/Event-controlled tests reproduce cancellation during resource acquisition and
writes, including repeated cancellation, without guessing a scheduling delay.

An initial full run exposed a timing race in the old combined deadline/shutdown test:
a 10-ms sleep could overrun its 50-ms deadline on a loaded machine. The deadline test
still verifies admission timeout. A separate shutdown test now awaits an explicit
request-start Event with an independent budget, instead of assuming the sleep duration.

These measure local scheduling overlap with a request double, not Telegram bandwidth,
backend buffers, process RSS, competitor performance or a production speed guarantee.
No network throughput claim is made. See [methodology](../design/performance-plan.md).

## Compatibility, security and status

Python >=3.11; the four versions above were actually tested on Linux. Persistent
storage still requires POSIX flock; other OS compatibility is not established. Session
format remains version 1. Independent schema snapshot/metadata are unchanged: advertised
layer 225, 1573 constructors and 783 methods; runtime raw bindings remain layer 229.
The independent declarations are offline-only. Generated counts are not live coverage.

Implemented and deterministically tested: concurrent upload window, ranged byte
streams, ownership/cleanup, strict range/part validation and public forwarding of
options. Partially verified: all Telegram runtime behavior remains dependent on the
backend, without account interoperability evidence. Experimental: independent native
handshake/codec tooling. Unsupported: CDN decryption, cross-DC media authorization,
expired-reference refresh, automatic resume, parallel downloads and dedicated media
connections, durable callback journal and fully bounded backend update queues.

Bounds cover this pipeline, not the backend's total buffering or arbitrary application
concurrency. Source/destination contents are not logged. Local paths are supplied by
the application, never inferred from a server filename. Nearby bytes can be fetched
at a range edge, though only the selected range is exposed. No independent file-hash
verification was added. Session plaintext-at-rest and prior security limitations remain.
No new dependency audit or independent cryptographic review is claimed in this increment.

## Next priorities and release blockers

1. Dedicated opt-in account/bot tests for auth, message/media exchange, state recovery
   and controlled disconnects/migrations/waits. Never place credentials in source.
2. End-to-end update backpressure and durable application acknowledgment/cursor state.
3. Cross-DC file authorization, reference refresh, authenticated CDN handling and
   verified file hashes before automatic media recovery/resume promises.
4. Independent crypto/runtime review and resolution of schema/runtime layer divergence.
5. Realistic transfer/dispatch/session profiling and OS verification before a production
   readiness or performance-superiority claim.
