# GramFlux 0.3.0a1 verification report

This is an independent MTProto alpha, not a production release candidate. Telethon,
Pyrogram and Hydrogram are neither runtime dependencies nor fallback engines.

## Architecture and implementation

The native engine implements RSA_PAD/DH authorization-key establishment, vetted
AES primitives with protocol IGE glue, MTProto 2.0 envelopes, SRP password proofs,
full/intermediate/abridged TCP framing and bounded concurrent request correlation.
Acknowledgments, containers, gzip limits, replay rejection and validated salt/clock
correction are native. Two reserved heartbeat slots avoid starvation by application
requests; CPU codec/crypto work runs outside the event loop with joined cancellation.
Ambiguous disconnected application requests fail rather than being blindly replayed.

Native update handling tracks global/channel counters, detects gaps and requests
differences. Counter commits follow handler completion. SQLite/memory sessions,
explicit saved/new/temporary session modes, authentication prompts, event filters,
message/history/dialog operations and streaming uploads/downloads use this engine.
These user-facing operations have controlled tests; this does not prove account-level
interoperability with Telegram.

Raw requests and codec use the same pinned official layer 225: 1,573 constructors
and 783 functions (2,356 API declarations). The special vector constructor is handled
by the codec; 1,572 ordinary constructors have generated minimal round-trip coverage.
There are 46 pinned MTProto declarations. Schema provenance and hashes ship in
`gramflux/tl/data`; declaration coverage is separate from working RPC coverage.

## Verification

Run from the repository root:

```sh
.venv/bin/ruff check .
.venv/bin/ruff format --check .
.venv/bin/mypy src
.venv/bin/pytest -q
.venv/bin/python -m gramflux.tools.schema verify
.venv/bin/python -m build
GRAMFLUX_NATIVE_NETWORK=1 .venv/bin/pytest tests/integration/test_native_live.py -q
.venv/bin/python -m gramflux.tools.native_probe --mode intermediate
.venv/bin/python -m gramflux.tools.native_benchmark
```

All quality checks passed: 106 formatted files; mypy checked 45 source files.
The offline suite passed **381 tests**, with **4 opt-in tests skipped** and four
FFDH deprecation warnings. Built-wheel tests also passed on Linux x86-64 using
Python **3.11.17, 3.12.3, 3.13.16 and 3.14.8** in isolated environments with no
Telethon installed. Each tested wheel was explicitly reinstalled and imported
from its environment's site-packages. Other operating systems are CI targets,
not locally verified platforms.

Three opt-in real-network tests passed: anonymous authorization-key establishment
and encrypted ping/pong against Telegram over all three supported TCP modes.
They require no user credentials and do not authenticate an account. Probe evidence
is in `research/native-telegram-probe.json`. The anonymous API probe received
`CONNECTION_NOT_INITED`; it is not counted as a successful application RPC.
A destroy-auth-key attempt ended in connection closure without parsed confirmation:
key destruction is **unconfirmed**, not successful. Probe keys are never persisted.

Protocol tests include an independent OpenSSL AES-IGE known-answer vector, RSA_PAD
recovery, DH peer agreement, SRP server algebra, tampered envelopes, out-of-order
responses, deadlines/cancellation, salt/clock rejection, bounded queues, replay,
update gaps and transfer interruption. Local loopback tests exercise actual TCP
framing. None substitutes for authenticated Telegram tests.

## Dependencies, performance and security

The sole direct runtime dependency is `cryptography==50.0.2`; its transitive runtime
requirements are locked. The recorded dependency scan found no known vulnerabilities;
this is not a cryptographic audit. Protocol constants and public key provenance are
recorded in `tl/data/trust.json` and `THIRD_PARTY_NOTICES.md`. No competing client
implementation was copied into the engine.

`research/native-ige-benchmark-0.3.0a1.json` records a reproducible local 512 KiB,
five-round comparison of our original bytewise XOR glue with our integer XOR glue:
median 0.231173 s versus 0.081360 s. This measures one local transformation, not
Telegram throughput or superiority over another library. Python IGE remains a
profiling target. Codec results are recorded separately; no network performance
claim is made.

Sensitive TL representations omit values, routine errors/logging omit payloads,
server input sizes are bounded, and session files use restrictive permissions where
supported. Session keys remain plaintext at rest. Python cannot guarantee zeroization.
Python bigint SRP and protocol glue have not received independent timing/security
review. The provider deprecates finite-field DH required by Telegram; the version is
pinned, but a maintained provider strategy is still required.

## Feature status and release blockers

| Area | Evidence/status |
| --- | --- |
| Native TCP, key exchange, encrypted ping | Unit/protocol tests and real Telegram tests |
| TL generation and native raw codec | Deterministic verification and controlled round trips |
| User/bot login, 2FA and session reuse | Implemented, controlled tests; account interoperability unverified |
| Messages, events, difference recovery | Implemented, controlled tests; live authenticated behavior unverified |
| Upload/download streams and cancellation | Implemented, boundary/interruption tests; live transfer unverified |
| Crypto hardening | Known-answer/negative tests; independent audit outstanding |
| Automatic reconnect/replay of pending RPCs | Unsupported; explicit failures preserve ambiguous outcomes |
| Proxies, CDN, resumable transfers, secret chats | Unsupported |

Release priorities, in order: authenticated test-account interoperability (including
DC migration, 2FA, updates and files); independent protocol/crypto review and FFDH
provider maintenance; verified key destruction and service-message coverage;
durable update recovery and reconnect semantics; representative network profiling.
Do not deploy as a production replacement on the strength of anonymous ping tests.

## Breaking changes from 0.2

Use native `gramflux.raw` objects and keyword arguments; foreign client objects are
rejected. Raw timestamps are Unix seconds. No external client session-file
compatibility is claimed. Refer to the migration guide and explicit session modes.

For each isolated interpreter, the executed wheel verification was equivalent to
(the four environment suffixes were `311`, `312`, `313`, `314`):

## Native runtime reliability follow-up

Fourteen additional regression cases cover TCP preamble deadline/cancellation,
full-transport counter reset on socket reuse, duplicate-open rejection, native
sender cleanup on setup errors, initialization rejection/uncertainty, a silent
handshake peer over real loopback TCP with clean retry, and event metadata retention.
Initialization policy follows the official [invokeWithLayer](https://core.telegram.org/method/invokeWithLayer)
and [initConnection](https://core.telegram.org/method/initConnection) wrappers.
No failed application request is automatically replayed to restore initialization.

The update path now preserves a batch's full entities in the public peer cache once;
each message event holds only chat, sender, via-bot and forwarding peers. This avoids
copying and repeatedly ingesting the full 4,096-entry cache per message. Forwarded
peer references and detached event metadata have regression coverage.

Run `.venv/bin/python -m gramflux.tools.update_benchmark` to reproduce the local
five-round comparison against GramFlux's previous full-snapshot emission code.
`research/native-updates-benchmark-0.3.0a1.json` records 10,000 events per round:
at 4,096 cached entities, medians were 0.516866 s versus 0.114985 s, with separately
measured traced peak allocations of 301,336 versus 2,248 bytes. At 64 entities the
new path was slower (0.106408 s versus 0.059279 s); at 1,024 entities it was faster
(0.096492 s versus 0.149484 s). These numbers exclude the public dispatcher,
network, encryption and application handlers. They do not establish overall client
speed or superiority over competitors. The workload keeps only the last event.


## Update-state correctness follow-up (2026-10-21)

Added 23 regression cases around independent pts/seq ordering, overlap suppression,
combined envelope starts, malformed sequence ranges, invalid/regressive authoritative
snapshots, stalled pages, recursive channels, short-message metadata and cancellation
of later channel pages. Source and installed-wheel verification cover these cases.
See [the update-state design](../design/update-state.md) for precise policies.
These controlled tests do not establish authenticated Telegram interoperability.

Commands run for this follow-up included `ruff check .`, `ruff format --check .`,
`mypy src`, `pytest -q`, `python -m gramflux.tools.schema verify`, `python -m build`
and `python -m twine check --strict` on the 0.3.0a1 wheel/source artifacts. The same
wheel installation/import checks and complete test command above were repeated in
all four clean interpreter environments. Existing anonymous-network evidence remains
separate from the new controlled update-state tests.
